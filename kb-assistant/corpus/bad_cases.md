## BC-2「切片时 overlap 设成 0 会发生什么？」 ✅ 已修复（2026-11-13, Day 16）

## Bad Case 详情

### BC-1 ❌「切片大小一般设多少合适？」→ 检索没召回

**模型原话**："资料中没有关于切片大小的具体数值或建议。"

**事实**：语料 `how_to_chunking.md` 第 95-97 行明确写着经验值——对话问答 256-512 token / 知识库检索 512-1024 token / 长文档摘要 1500-2000 token。

**定位证据**（检索 Top-5 实拍）：经验值段落**不在 Top-5 里**，且 Top-5 中有 2 个名额被文档头部的 title/tags 元信息垃圾块占据（rank 1 和 rank 3）——5 个名额浪费 40%。

**初步观感**：病因大概率在检索侧。切片时没有做清洗，元信息块和正文混在一起被切被编码；经验值段可能被切进某个"不显眼"的片里，向量离问题远。→ Day 16-17 切片优化 + 清洗的首要靶子。

**Day 15 诊断补充（2026-11-13）**：
- 全库 50 片检索实测：经验值段排在**第 12 名**（相似度 0.442），K=5、K=10 都够不着它；
- **切片质量实锤**：这个片的开头是"50 个 token 的内容，但这 2000 token 都会被塞进 Context…"——固定长度切分把「chunk 太大的害处」（第 93 行）和「chunk 大小经验值」（第 95-97 行）**焊在了同一片里**，片的开头是另一个话题，向量被前半部分主导，"256~512 token" 这个关键信号被稀释；
- **病因排序修正**：① 垃圾块占 Top-5 两席（清洗可解）② 切片边界把目标段与无关内容焊接（换切分策略可解）③ K=5 偏小（治标：K 得开到 12+，代价是约 4000 token 全塞进 Prompt，且垃圾更多）；
- Rerank 辨析：Rerank 只能重排**已捞进候选池**的片段，捞不上来的它变不出来——它治排序（precision）不治召回（recall）。但"宽召回 top-50 + Rerank 精选 5"的组合拳确实能救这个 case（cross-encoder 能深度交互，把 0.442 的它拉上来）。所以正确因果链是：先扩大候选池，Rerank 才有用武之地。

### BC-2 ❌「切片时 overlap 设成 0 会发生什么？」→ 召回了但过于保守

**模型原话**："资料中没有……直接说明。资料中只提到 overlap 的作用是防止重要信息落在 chunk 边界被割裂……但并未说明 overlap 设为 0 时的具体后果。"

**事实**：语料第 70-72 行写了 overlap 的解决思路（相邻 chunk 保留重叠区）。由"overlap 的作用 = 防边界割裂"一步就能推出"设为 0 = 失去保护，边界信息会丢"——这是**一步推理**，不需要新知识。

**初步观感**：检索没毛病（相关片段召回了，模型还引用了 [1][2]），病因在生成端：规则 3"不足直说"让模型变得过于保守，宁可拒答也不肯做一步推理。→ 优化方向：Prompt 措辞调整（如"资料给出原理时，可以据此推断直接后果"），属生成侧低成本修复。

## 顺手记下的检索质量观察

- **垃圾块占用名额**：Top-5 里 title/tags 元信息块反复出现（BC-1 实拍 2/5），它们关键词密度高（"Chunking""Overlap""RAG优化"），向量离各类问题都近——**清洗 + 结构感知切分前，这个问题会一直存在**。
- **相似度分数手感**（cosine 空间）：强相关 ~0.8+，沾边 0.5-0.6，无关 ~0.35。BC-1 的教训：**分数低 ≠ 语料里没有**——0.5-0.6 的"沾边"段可能就藏着正确答案，Top-5 塞不下而已。
