# 容量报告（Day 33 压测，2026-11-16）

## 1. 测试环境与配置

| 项 | 值 |
|---|---|
| 机器 | 本机 Windows 11 笔记本，**纯 CPU**（无 GPU） |
| 检索链路 | bge-small-zh-v1.5（本地 CPU 编码）+ BM25 + bge-reranker-base（本地 CPU 精排 20 对）+ DeepSeek API 生成 |
| 关键参数 | POOL=20，K=5，MAX_CONCURRENT=8，缓存击穿（每题加随机后缀） |
| 压测工具 | locust 2.47，4 并发用户，60 秒，ramp 1 用户/秒 |
| 数据量 | 语料 718 片（kind=course 参与检索） |

## 2. 结果

| 指标 | 数值 |
|---|---|
| 总请求 | 26（POST /api/chat 17 + SSE 流式 6 + 探活若干） |
| 失败率 | **0%** |
| 吞吐（聚合） | **0.5 req/s**（单机纯 CPU 的瓶颈值） |
| POST /api/chat 延迟 | P50 8.8s ｜ **P95 10.0s ｜ P99 10.0s** |
| **TTFT（首字时间）** | 平均 **7.1s** ｜ P50 7.4s ｜ P95 9.1s ｜ 最快 3.7s |
| 并发闸门拒绝 | 0（4 用户 < 上限 8，未触发） |

## 3. 瓶颈拆解（本报告最重要的结论）

单次请求的耗时构成：

```
问题 → bge 编码(~0.2s) → BM25(~0.05s) → 精排 20 对×512 token(本地 CPU ~5-6s!)
     → 拼 Prompt → DeepSeek 首 token(~1s) → 生成(~2-3s)
     └────────────── TTFT ≈ 7s ──────────────┘
```

**TTFT 的大头不是大模型，是本地的 Cross-Encoder 精排**——20 对 (问题, 片段) 在 CPU 上打分占了约 5-6 秒。这推翻了“AI 服务慢是因为 LLM 慢”的直觉，是容量规划的关键发现。

## 4. 成本（实测）

- 26 次真实问答：输入 28,601 token / 输出 3,536 token ≈ **0.086 元**（按 2/8 元每百万 token 估算）
- 折算：**约 3.3 元 / 千问**；日均 1000 问 ≈ 3.3 元/天
- 默认预算 200,000 token/天 ≈ 140-180 问/天（约 0.6 元/天）——个人/小团队够用，团队上量需调预算

## 5. 优化建议（按 ROI 排序）

| 措施 | 预期收益 | 代价/风险 |
|---|---|---|
| POOL 20 → 10 | TTFT 约 -2~3s（精排量减半） | 需评测验证 Top-5 质量不掉 |
| K 5 → 3 | 生成输入 token -30%，总延迟 -1s | 上下文完整度下降（测评裁决） |
| 真实用户缓存命中 | 重复问题**秒回**（实测 5.9s → 0.07s） | 无 |
| Rerank 迁 GPU / 换 API | TTFT 降到 2s 级 | 增加部署复杂度/费用 |
| bge 编码批量化/ONNX | 编码路径小幅提速 | 工程改造 |

## 6. 结论

当前配置（单机纯 CPU）能稳定支撑 **~0.5 QPS、4 并发无拒绝、0 失败**的小范围使用（个人学习、小团队内部）；作为“发给朋友试用”的部署规模完全够用。若面向生产，第一步优化应瞄准 **Rerank 的 CPU 开销**，而不是模型 API。
